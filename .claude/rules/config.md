# Configuration Loading

- `SpawnConfig`: global config from `~/.config/incus-spawn/config.yaml`
- `ImageDef.loadAll()`: discovers all image definitions across resolution layers
- `ToolDefLoader`: discovers tools across resolution layers
- `ProjectConfig`: per-project config from `incus-spawn.yaml` or `.incus-spawn/incus-spawn.yaml`

Resolution order for both images and tools (later overrides earlier): built-in -> user (`~/.config/incus-spawn/`) -> search paths -> project-local (`.incus-spawn/`).

**Project-local is untrusted**: it is whatever a cloned repo ships. Project-local templates' host-resources are confined to the project directory (`ImageDef.projectRoot` stamped at load, never from YAML; enforced in `HostResourceSetup.collectEffective()`, re-checked via `verifyConfined()` at build, branch, and start; recorded in `BuildSource.projectRoots`). A `file://` base image URL in a project-local template gets the same check (`BuildCommand.requireConfinedBaseImages`). Project-local templates get no host repo references and are skipped by `HostRepoRefresh.collectAllRepos()`. Their `image_url` may only replace an image their own project imported (`incus-spawn.project` image stamp; trusted builds refuse or re-import project-stamped images, `BuildCommand.requireImageTrustedFor`). Project-local tools cannot declare `proxy:` (`ToolProxyResolver.rejectProjectLocalProxy()`). Any new capability that reaches host state outside the project, such as host paths, host-only sources, or credentials, needs the same gate. See DESIGN.md "Project-local templates are confined to their project".

**Secrets**: `SecretRegistry` is the single source of truth for *where secrets live* in `config.yaml`. It holds no list -- it collects every tool's `ToolDef.ConfigEntry` that declares `secret: true` with a `config-path`, resolved through `ProxyDef.fullConfigPath()`. So a new credential is made known to every secret-aware consumer by declaring it on the tool (Java `ToolSetup.proxy()` or tool YAML), never by editing a list here; the same declaration that makes the proxy inject it makes the redactor remove it. `SecretRedactor` is the first consumer (`isx doctor --bundle`: structural redaction of the config, then value/pattern scrubbing of logs, marker `<isx:redacted:<path>>`); a pluggable secrets backend would be the second. The split is deliberate: `SecretRegistry` knows *where declared secrets live*, `SecretRedactor` knows *what a credential looks like* -- its `looksSecret()` whole-word name heuristic (a backstop for undeclared keys landing in `SpawnConfig.extras`; keep it whole-word, since substring matching blanks out unrelated diagnostics like `monkey` and `keyboardLayout`; and the nearest key name governs — a secret-named *list* is redacted whole, a secret-named *object* is not, since its fields have their own names and an `auth: {endpoint, timeoutMs}` block is ordinary config) and its token-shape patterns. See DESIGN.md "Support bundles: redaction by construction".

**Credential accounts**: each credential namespace may hold `accounts:` (a named map) and `default:`. `AccountResolver` resolves them off the serialized config tree, so any namespace gets named accounts without a Java change -- including a tool defined only in YAML, whose namespace lands in `SpawnConfig.extras`. **One model for every namespace, Claude included (#773)**: a namespace with no `accounts:` block but a flat credential (`github.token`, as every pre-accounts file has) *presents as the account `default`* -- listed, pinnable as `<ns>=default`, served -- with nothing synthesized into the file (`value()` falls back from the account's key to the flat one). What the resolver knows about a namespace is its `AccountShape`, from `ToolSetup.accountShape()`: derived from the proxy definition by default (`secret: true` entries are the credential, so `apiKey: ""` or a lone `github.email` is not an account; user-supplied entries are per account; `confirm` entries stay shared at the namespace level), overridden by `GhSetup` (email is per account) and `ClaudeConfig.ACCOUNT_SHAPE` (flat `useVertex`, type-dependent completeness). Its `problem()` hook is the only per-namespace judgement: unusable accounts are skipped for the default and a pin to one fails as "configured but incomplete" (#742). Tree-taking resolver methods take the shape explicitly (the proxy passes the setups it holds -- never scan tool YAMLs on the event loop); `SpawnConfig`-taking ones look it up, built-in Java tools first. **Do not add `if (namespace is claude)` branches** -- a namespace that needs different rules needs a different shape. Namespaces that *do* have a class (`GitHubConfig`, `BobConfig`, `OpenaiConfig`) extend `SpawnConfig.NamespaceConfig` to preserve undeclared keys; without that an `accounts:` block deserializes to nothing and the next `save()` **deletes it**. Any new nested config class holding credentials must extend it for the same reason, and its "is this configured" accessors must go through `NamespaceConfig.defaultValue()` -- the typed field is empty once the credential lives in an account. `ClaudeConfig` keeps a typed API (`accountNamed`, `accountFor`) only to *interpret* accounts (`effectiveType`, `servesDirectApi`). Secrets under `<ns>.accounts.<name>.<path>` are already covered by `SecretRedactor`'s deep pass under a declared namespace, so no separate registration is needed. `NamespaceAccounts` is the write side, and **always writes the accounts layout** (a single credential is `accounts.default` + `default: default`): `put`/`replaceAll`/`setDefault`/`remove`/`clear`; `put` and `remove` first call `materialize` (`replaceAll` and `clear` discard the flat credential outright), which moves a flat credential into `accounts.default` -- only on a write with something to save, so an abandoned `isx init` leaves the file untouched (#740). `isx init` drives it from the namespace name alone with one vocabulary for every namespace, `AccountTarget(name, replaceOthers)`, applied only once a credential is collected (`InitCommand.saveAccount`); GitHub, Bob, OpenAI and YAML tools share `chooseAccountTarget`, Claude keeps its own menu for its typed listing. `ImageDef.resolveAccounts()` merges a template chain's `accounts:` per key, and the selection is part of `contentFingerprint()` -- re-pointing an account changes what gets baked (Claude's auth mode, the git identity), so it must rebuild. Files written by releases users are on (v0.3.7, v0.3.8) are pinned by `PreviousReleaseConfigCompatTest` against fixtures generated by each release's own serializer (`scripts/config-compat/generate-fixtures.sh <tag>`); add the tag to its `RELEASES` and to the CI loop whenever a release changes the format or users stay on it. v0.3.7 still writes the old `host-path` key, beside `host-paths` naming the same path, which must load as one.

**Name conflicts vs. overrides**: Overriding a definition from a *later* layer is intentional and supported. Two files declaring the same `name:` *within a single directory* (usually a copy-paste that forgot to update `name:`) is always a mistake and is reported as a conflict. `ImageDef.loadAllWithConflicts()` / `ToolDefLoader.conflicts()` return these same-directory collisions (all colliding files, so 3+ are listed together) plus the intentional cross-layer overrides. `isx build` aborts with a message naming the colliding files and refuses to build until you disambiguate; the TUI stays resilient (surfaces the conflict as a status warning but still lists templates); `isx doctor` reports both conflicts (warnings) and cross-layer overrides (informational -- this explains the "built image doesn't match the file I'm editing" confusion). Plain `ImageDef.loadAll()` still returns the resolved map (last-writer-wins) and emits a one-line conflict warning via its warnings consumer, so existing callers are unaffected.
