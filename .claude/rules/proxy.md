# MITM TLS Proxy

`MitmProxy` (in `proxy/src/main/java/dev/incusspawn/proxy/`; the supporting `ProxyConfig`, `ProxyCredentials`, `ProxyHealthCheck`, `ProxyService` and `CertificateAuthority` live in `common/src/main/java/dev/incusspawn/proxy/`) is a TLS-terminating proxy that intercepts HTTPS to specific domains and injects real auth credentials, so containers only hold placeholder values. Key design:
- Listens on gateway IP:18443 (iptables redirects 443->18443 on the bridge)
- `authError` is set by credential injection, which only runs on **real container traffic** -- so on its own it makes the status wrong in both directions (a fixed failure still shown, a broken credential not yet noticed). `/health` therefore verifies the Vertex token itself via `claimAuthRevalidation()`, running `getVertexAccessToken()` through `executeBlocking` (it forks `gcloud`; never call it on the event loop from here). The gate declines in four cases and each one matters: **not `useVertex()`** (first line, before any lock or dispatch -- non-Vertex users must pay nothing); **a fresh cached token with no error** (`hasFreshVertexToken()`, read *outside* `authLock` -- taking `authLock` then the instance monitor while the traffic path takes them in the other order would risk deadlock); **a standing non-`VERTEX_AUTH_HINT` error** (OAuth needs `isx init`); and **the 10s throttle / in-flight flag** (a failing credential caches nothing, so every poll would otherwise fork `gcloud`). A probe failure calls `recordProbeAuthError`, **not** `setAuthError` -- the latter notifies, and the check runs on every poll. When adding a new credential source, give it a hint constant and decide explicitly whether it is machine-verifiable.
- `getVertexAccessToken()` is bounded at `GCLOUD_TIMEOUT_SECONDS` and rejects an empty token instead of caching it. Both matter because `/health` reaches this with no traffic to reveal a wedged `gcloud` or a blank credential.
- The proxy authenticates to Vertex with `gcloud auth print-access-token`, which reads the **gcloud user credential** -- so the remediation is `gcloud auth login`, not `gcloud auth application-default login`. `InitCommand.verifyVertexConfig()` uses the same command and must give the same hint.
- Per-domain certs signed by a custom CA (installed in templates during build). The CA lives at `~/.config/incus-spawn/ca.{crt,key}`; leaf certs are persisted by `CertStore` under `~/.config/incus-spawn/certs/` (`<domain>.crt`/`.key`, wildcards as `_wildcard.<domain>`) and reused across proxy restarts, re-minting only on miss/CA-rotation/near-expiry. Persisting is what keeps each leaf's `notBefore` stable: the proxy is relaunched frequently (macOS launchd `KeepAlive`), and re-minting on a host whose clock has jumped ahead of a lagging container clock (e.g. an Incus VM after macOS resume) produced certs the container rejected as "not yet valid". Certs are keyed by domain, never by container (a leaf is a function of `(domain, CA)`), so this composes with future per-container interception, which is a routing/DNS concern. `CertificateAuthority.BACKDATE_MS` backdates `notBefore` as a skew margin for the rare fresh-mint moments.
- Both CA and leaf certs carry RFC 5280 key identifiers: SKI on the CA, SKI + AKI on leaves. Strict validators (OpenSSL 3.5, and so Python 3.13+, which turns on `VERIFY_X509_STRICT` by default) reject a chain without them -- including the trust anchor, so leaf-only extensions are not enough. A CA generated before this is re-issued on load over its **existing key** (`reissueWithSki`), which keeps every leaf valid and un-re-minted; the replaced cert is kept as `ca-superseded.crt`. Images stamped with that superseded fingerprint carry a stale-but-not-foreign anchor: `BranchCommand` lets them branch (the new cert is pushed into the instance by `InstancePrep`/`fixContainerCaIfNeeded` on first use) instead of demanding a rebuild the way a real CA rotation does.
- Three auth modes for Anthropic domains (priority: Vertex > OAuth > API key): OAuth mode strips `x-api-key` and injects `Authorization: Bearer <token>` for Claude Pro/Max users; Vertex mode does three-way routing -- passthrough for Vertex-formatted requests, standard-to-Vertex translation for `/v1/messages` (using `VERTEX_ALLOWED_FIELDS` body allowlist), and direct forwarding for non-messages endpoints; API key mode replaces `x-api-key` with the real key. Anthropic auth is declared via `ClaudeSetup.proxy()` with `type: anthropic` but remains hardcoded in `MitmProxy` (too complex for the generic tool proxy system); `applyToolProxies()` filters `type: anthropic` entries from domain maps
- GitHub, Bob, and Codex/OpenAI credential injection is handled via tool-contributed proxy entries (see Tool System), not hardcoded. `ToolProxyResolver.resolve(SpawnConfig)` resolves configuration from `value`/`config-path`, uses `${configKey}` template substitution in auth fields, and produces a per-domain `ResolvedToolProxy` list. `MitmProxy` stores these in `toolProxyByExactDomain` (exact matches) and `toolProxyWildcardSuffixes` (wildcard suffix matches); `findToolProxy()` does exact-then-wildcard lookup. `isInterceptedDomain()` is an instance method (not static) to include tool proxy domains alongside built-in ones. `ProxyCredentials` only has Anthropic-specific fields (`anthropicApiKey`, `oauthToken`, Vertex settings) -- `ghToken`/`bobApiKey`/`openaiApiKey` have been removed
- WebSocket passthrough: handles Upgrade requests by establishing an upstream WebSocket connection (with credential injection via both Anthropic auth and tool proxy lookup), then relaying frames bidirectionally with keepalive pings and close-code propagation. Used by Codex CLI for `api.openai.com`
- Caches OCI blobs by SHA256, Maven artifacts by coordinate, and npm tarballs from `registry.npmjs.org` with ETag-based packument verification
