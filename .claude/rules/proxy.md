# MITM TLS Proxy

`MitmProxy` (in `proxy/src/main/java/dev/incusspawn/proxy/`; the supporting `ProxyConfig`, `ProxyCredentials`, `ProxyHealthCheck`, `ProxyService` and `CertificateAuthority` live in `common/src/main/java/dev/incusspawn/proxy/`) is a TLS-terminating proxy that intercepts HTTPS to specific domains and injects real auth credentials, so containers only hold placeholder values. Key design:
- Listens on gateway IP:18443 (iptables redirects 443->18443 on the bridge)
- `authError` is set by credential injection, which only runs on **real container traffic** -- so on its own it makes the status wrong in both directions (a fixed failure still shown, a broken credential not yet noticed). `/health` therefore verifies the Vertex token itself via `claimAuthRevalidation()`, running `getVertexAccessToken()` through `executeBlocking` (it forks `gcloud`; never call it on the event loop from here). The gate declines in four cases and each one matters: **not `useVertex()`** (first line, before any lock or dispatch -- non-Vertex users must pay nothing); **a fresh cached token with no error** (`hasFreshVertexToken()`, read *outside* `authLock` -- taking `authLock` then the instance monitor while the traffic path takes them in the other order would risk deadlock); **a standing non-`VERTEX_AUTH_HINT` error** (OAuth needs `isx init`); and **the 10s throttle / in-flight flag** (a failing credential caches nothing, so every poll would otherwise fork `gcloud`). A probe failure calls `recordProbeAuthError`, **not** `setAuthError` -- the latter notifies, and the check runs on every poll. When adding a new credential source, give it a hint constant and decide explicitly whether it is machine-verifiable.
- `getVertexAccessToken()` is bounded at `GCLOUD_TIMEOUT_SECONDS` and rejects an empty token instead of caching it. Both matter because `/health` reaches this with no traffic to reveal a wedged `gcloud` or a blank credential.
- The proxy authenticates to Vertex with `gcloud auth print-access-token`, which reads the **gcloud user credential** -- so the remediation is `gcloud auth login`, not `gcloud auth application-default login`. `InitCommand.verifyVertexConfig()` uses the same command and must give the same hint.
- Per-domain certs signed by a custom CA (installed in templates during build). The CA lives at `~/.config/incus-spawn/ca.{crt,key}`; leaf certs are persisted by `CertStore` under `~/.config/incus-spawn/certs/` (`<domain>.crt`/`.key`, wildcards as `_wildcard.<domain>`) and reused across proxy restarts, re-minting only on miss/CA-rotation/near-expiry. Persisting is what keeps each leaf's `notBefore` stable: the proxy is relaunched frequently (macOS launchd `KeepAlive`), and re-minting on a host whose clock has jumped ahead of a lagging container clock (e.g. an Incus VM after macOS resume) produced certs the container rejected as "not yet valid". Certs are keyed by domain, never by container (a leaf is a function of `(domain, CA)`), so this composes with future per-container interception, which is a routing/DNS concern. `CertificateAuthority.BACKDATE_MS` backdates `notBefore` as a skew margin for the rare fresh-mint moments.
- **Certs are chosen per SNI name** by `InterceptedCertOptions` (Vert.x `keyManagerFactoryMapper`, run on a worker thread), not by a fixed keystore. dnsmasq sends names at *any* depth under an intercepted domain, but a wildcard SAN covers one label, so `certNameFor()` gives the exact domain or a wildcard for the name's own parent, minted on demand through `CertStore`. Two bounds, because the container picks the names: `MAX_ON_DEMAND_CERTS` counts on-demand certs **on disk** (so reloads/restarts don't reset it), and `MAX_SERVED_NAMES` counts distinct SNI names answered, since Vert.x caches an `SslContext` per answered name forever. With the old `<domain>`/`*.<domain>` JKS, a deeper name matched no alias and Vert.x served an arbitrary entry: `*.api.openai.com` for a GitHub host (#783). Anything else (off-domain, no SNI, over the cap) is refused: the mapper returns `null` and the default key manager holds **no** cert, so the handshake fails at once. Never refuse by throwing from the mapper -- Netty then hangs the connection until the handshake timeout. SNI names become file names, so `CertStore.get()` accepts only `CertStore.isHostname` names. `InterceptedCertOptionsTest` covers every shipped intercepted domain automatically.
- Both CA and leaf certs carry RFC 5280 key identifiers: SKI on the CA, SKI + AKI on leaves. Strict validators (OpenSSL 3.5, and so Python 3.13+, which turns on `VERIFY_X509_STRICT` by default) reject a chain without them -- including the trust anchor, so leaf-only extensions are not enough. A CA generated before this is re-issued on load over its **existing key** (`reissueWithSki`), which keeps every leaf valid and un-re-minted; the replaced cert is kept as `ca-superseded.crt`. Images stamped with that superseded fingerprint carry a stale-but-not-foreign anchor: `BranchCommand` lets them branch (the new cert is pushed into the instance by `InstancePrep`/`fixContainerCaIfNeeded` on first use) instead of demanding a rebuild the way a real CA rotation does.
- Claude credentials live in `claude.accounts`, a named map (`ClaudeAccount`, `type: api-key|oauth|vertex`) so several accounts can be configured at once; `claude.default` names the one instances use. `ClaudeConfig.accountFor(Predicate)` picks the default when it qualifies, else the first that does. Which accounts exist and which is the default are answered by `AccountResolver` against `ClaudeConfig.ACCOUNT_SHAPE`, the same rule as every namespace (a pre-accounts flat file presents as the account `default`; see `config.md`), so nothing outside `ClaudeConfig` branches on Claude. `ClaudeConfig`'s `isOauthMode()`/`getApiKey()`/`isUseVertex()` accessors are **derived from the resolved account**, so `ProxyCredentials`, `ClaudeSetup` and `PiSetup` read them unchanged. Both config classes bind Jackson **by field** (`@JsonAutoDetect` getters `NONE`) because the derived getters collide with the legacy field names -- an `@JsonIgnore` there disables the whole split property and a flat `config.yaml` silently stops deserializing. Account selection is **per instance** and **generic across config namespaces** -- see the next two bullets.
- **Per-instance accounts.** Three layers, resolved lowest-first: the namespace's `default` in config.yaml, the template's `accounts:` map (merged per key down `ImageDef.chain()` via `resolveAccounts`), and a per-instance override (`isx branch --account <ns>=<account>`, `isx account set`; `isx account unset` removes it). The last two are stamped as `user.incus-spawn.account.<namespace>` (`Metadata.accountKey`). Selection is always namespaced -- a bare name would fan out over whichever namespaces happened to have that account, so a namespace added later would silently widen an existing command. **Fail closed**: a pin to an account that is gone raises `AccountResolver.UnknownAccountException` and the request 502s; never fall back to the default, which in #351's case belongs to another client. `isx doctor` reports dangling pins. `AccountUsage` is the read-side view for humans (`isx account show`): the served account per namespace, who chose it -- recorded beside every pin as `user.incus-spawn.account-origin.<ns>` (`AccountOrigin`: `template:<name>`, `explicit`, `copied:<instance>`), written only through `AccountSelection.stampUpdates` so pin and origin never diverge -- and drift from the template's current `accounts:`; `ToolSetup.describeAccount()` describes an account without its credential. `isx init` warns before removing an account pinned by instances or named by templates, and its rename re-points pins via `AccountSelection.renameInInstances`, which renames an identity stamp only through `ToolSetup.renameBakedIdentity()` (GitHub keeps the fingerprint). **Default changes** move every unpinned instance: `isx init` (`changeDefaultAccount`) names them (`InstanceRegistry.accountStates` includes unpinned instances) and offers switch/keep/cancel; the proxy logs them on reload (`logDefaultChanges`). The registry reads `account-identity` stamps (`InstanceAccounts.bakedIdentities`), and `MitmProxy.refuseIfUnservable` fails closed -- `AccountSelection.UnservableAccountException`, 502 -- when the served account (pin or default) needs another Claude auth mode than the instance was built with (`AccountSelection.servingMismatches`), scoped to that credential's domains (`namespacesForDomain`, wildcards included); cached per registry record in the reload's `ConfigState`, so a result computed from the old config lands in a cache nothing reads any more. `accountStates` lists branches only -- never templates, whose pins would travel to all their branches.
- **The generic seam is one method.** `ProxyDef.accountConfigPath()` builds `<ns>.accounts.<account>.<config-path>` beside the existing `fullConfigPath()`; `ToolProxyResolver.resolveConfigValue` prefers it and falls back to the flat path when the namespace has no accounts *or the account omits that key* (a namespace may hold the token per account and other settings globally). That gives named accounts to every namespace at once, YAML-only tools included, with no per-tool code. The namespace is derived **per config entry** (`ProxyDef.namespaceOf`), not per tool: a tool may *borrow* another namespace's credential by naming it fully in `config-path` and declaring no `config-namespace` (`CopilotSetup` points at `github.token` to share the `gh` PAT). Keying off the tool's own namespace would leave `gh` authenticating as the pinned account while copilot used the flat token -- two GitHub identities in one container. `AccountResolver` does the tree-based resolution; `AccountSelection` does parsing/validation/stamping. `GitHubConfig`/`BobConfig`/`OpenaiConfig` extend `SpawnConfig.NamespaceConfig` so an `accounts:` block survives a save -- without it the block deserialized to nothing and the next save **deleted** it.
- **Caller identification.** `routeRequest`/`routeWebSocket` read `req.remoteAddress()`; iptables REDIRECT preserves the container's source address, and every branch has a static IP in `Metadata.STATIC_IP`. `InstanceRegistry` maps address -> (instance, accounts) from one `listJsonConfig()` call. An address two instances claim (a copy made before #815, or by `incus copy`) belongs to the one running claimant -- Incus will not start a second NIC on the same address -- and to nobody when none or several run; never to whichever is listed last. `isx branch`/`isx account set` poke it with **SIGUSR1** (`ProxyService.signalAccountRefresh`), not SIGHUP: pinning is instance state, and answering a branch -- the most common operation there is -- with a full reload would re-mint certs and re-push SSL options every time. `lookup()` must stay non-blocking (event loop); refreshes go through `executeBlocking` with single-flight, like `resolveHost`/`acquireVertexAccessToken`. Normalize `::ffff:` mapped addresses or every lookup misses and silently serves defaults. An unknown address gets the defaults on purpose: host traffic uses this proxy too. Build containers that pin an account are **not** unknown (#903): `BuildAccounts.start` claims them an address (`InstanceLifecycle.assignBuildAddress`, filtering on, guest keeps DHCP, leased addresses skipped) and stamps the template's pins before the first start, clears every `account-identity` stamp copied from the parent (else `refuseIfUnservable` would refuse the build its own template's account, or a changed default) -- reading them first, since `settleIdentities` needs them after tool setup and `BuildAccounts.identityStamps` puts back the ones the build does not re-stamp -- and signals the proxy; `releaseBuildAddress` gives the address back once the template is stopped. A build pinning nothing is served the defaults either way and keeps plain DHCP. A new build path must do the same before anything in it goes through the proxy.
- **The instance secret (#934)** is a second layer on the address, never a replacement: `InstanceRegistry.identify(address, secret)` passes only when both belong to one instance (`InstanceSecret.matches`, constant time; no hash recorded means nothing passes). The host holds only the SHA-256 (`Metadata.INSTANCE_SECRET_SHA256`; a guest reads its own `user.*` keys via `/dev/incus`), kept in the snapshot's `secretByAddress`, not in `InstanceAccounts`, which `MitmProxy` caches by value. Every isx start rotates it: `BranchFlow.create` (hash on the copy request, secret to `setupRuntime`), `InstanceLifecycle.startForUse`/`restartForUse` (`rotateInstanceSecret` before the start, then the `waitForReady` probe writes `/run/isx/instance-secret`), and `VmAgentRecovery` (the hash in its boot-stamp write). A container start also records the boot it went to (`recordSecretBoot`: its `last_used_at`, read once the guest answers, as `Metadata.INSTANCE_SECRET_BOOT`; the read is returned for the CA check, `fixContainerCaIfNeeded(incus, name, instance)`, so the stamp's write is the only request added -- pinned in `InstanceLifecycleRequestBudgetTest`), so `ensureReady` can tell a reboot isx did not do from the instance it already holds and give the box a new secret (#1024); a VM is never stamped, since QEMU reboots in place, and its agent probe asks the guest instead (`InstanceSecret.GUEST_CHECK`). A new path that starts or restarts an instance for use goes through these or does the same; builds get none. The secret reaches the guest in the exec environment (`InstanceSecret.guestEnv` + `GUEST_SCRIPT`), never on a command line, which any guest user can read; the same exec reconciles the Claude Code registration of `mcp.isx.internal` with the `mcp-caller` grant every caller passes beside it (`McpClientRegistration`, #1182, see `mcp.md`). Rotation does not signal the proxy (cost on every start; a refusal right after a start refreshes and retries, throttled by `wantsMissRefresh()` like a lookup miss). See DESIGN.md "A per-start secret".
- **Guest tools read their placeholder when they run (#1108)**, because it becomes a per-start proof (#1106) the proxy checks (#1107). Nothing a build writes may hold one: `ClaudeSetup` and `CodexSetup` each write an `/etc/profile.d/isx-zz-*-auth.sh` login script (sorted after every `isx-*.sh`) that adapts the exported value to what the tool reads -- Claude Code's `customApiKeyResponses.approved` (last 20 characters of `ANTHROPIC_API_KEY`, else an interactive prompt defaulting to no), `ANTHROPIC_CUSTOM_HEADERS` from `ISX_VERTEX_ACCESS_TOKEN` (under `CLAUDE_CODE_SKIP_VERTEX_AUTH` Claude Code sends no Authorization header of its own), and Codex's `~/.codex/auth.json` (Codex never reads `OPENAI_API_KEY`). The `gcloud` stub prints `$ISX_VERTEX_ACCESS_TOKEN`; `GhSetup`'s host-driven `gh api` calls take `GH_TOKEN` from the guest's `/etc/profile` (`GhSetup.LOGIN_TOKEN`). gh, Copilot, Pi and Bob read the variable already. A child build refreshes these files for a tool it only inherits (`ToolSetup.refreshInherited`, from `BuildCommand.refreshInheritedTools`), so an older parent's files do not reach it. A YAML tool whose `files:` or build steps hold the value of one of its own credential-named env entries is warned about by the loader (`ToolDefValidator.embeddedTokens`). Per-tool evidence: DESIGN.md "A placeholder is read when the tool runs".
- **Proof tokens (#1106, toward #1100).** A started instance's credential placeholders are proofs of its login environment, not constants: `ProofToken.derive(secret, ns)` is HMAC-SHA256 keyed with the per-start secret over the namespace (32 hex), presented as the tool's prefix + `isx_` + digest (`gho_isx_…`). Keyed with the secret, never its hash, which a guest reads from `/dev/incus`. Which variables carry which namespace's proof is declared on the tool -- `placeholders:` (`env`, `prefix`) on its `proxy:` entry, in the tool's one credential namespace (`ToolSetup.credentialNamespaces()`), exposed as `ToolSetup.placeholders()` (pi overrides it for the one variable of its own) -- never listed by name; `ProofToken.declaredBy` drops unsafe declarations and a variable declared two ways (fail closed: the static placeholder proves nothing). The set is `ToolProxyResolver.proxyToolSetups` (no feature-gated-off or project-local proxy tool). `InstanceSecret.guestEnv(secret, placeholders)` carries the exports beside the secret in the same exec; `GUEST_SCRIPT` writes them to `/run/isx/proof-tokens` (0440, group 1000, previous proofs removed first) and `isx-instance-secret.sh` sources it after `isx-env.sh`; each line replaces a variable only while it holds the build's placeholder (`<prefix>placeholder*`) or an earlier proof (`<prefix>isx_*`), and only where the placeholder's guard holds (`Placeholder.onlyWhen`, code only: Claude's `ANTHROPIC_API_KEY` needs #1108's `isx-zz-claude-auth.sh` or no `~/.claude.json`, so a pre-#1108 Claude image keeps its approved static key until rebuilt). Every secret delivery carries them (branch setup script, `startForUse`, `restartForUse`, `VmAgentRecovery`, `giveSecretToThisBoot`); each reads the declarations off disk in the background while the instance is copied or starts (`ProofToken.declaredInBackground`), so the request budget is unchanged, and always without the current directory's `.incus-spawn/tools/` (`ToolDefLoader.withoutProjectTools`, as the proxy sees them: never the tool setups `BranchFlow.preflight` loads, which include it). A YAML tool's placeholder must be one of its own `env:` entries. Instances an older isx started get proofs at the next shell: a VM's probe checks the proofs file with the secret (`GUEST_CHECK`), and a container's boot stamp carries a mark that its delivery had proofs (`InstanceLifecycle.secretBootStamp`), so an older stamp no longer matches. A new path that delivers a secret passes placeholders too. The proxy does not verify them yet (#1107). See DESIGN.md "Proof tokens".
- **`mcp.isx.internal` is answered, not relayed (#915).** `routeRequest` hands `ProxyConfig.MCP_DOMAIN` to `McpBridge` before any other domain check (a WebSocket to it is refused): `isx mcp` over MCP's Streamable HTTP for an instance stamped `mcp-caller`, identified by `InstanceRegistry.identifyMcpCaller()` (address + secret + stamp; one throttled refresh on a refusal, as for `identify()`). Each session is a child `isx mcp --caller-instance <name>` (the `isx` beside `isx-proxy`, else `~/.local/bin/isx`, else PATH; tests swap the command with `useMcpCommand`), one per instance; the keepalive tick (30 s, under the 120 s idle timeout) also ends sessions whose instance lost the stamp, and `stop()` ends them all. Never block the event loop on the child: starting it runs in `executeBlocking`, its pipes on virtual threads. See `mcp.md`.
- **`security.ipv4_filtering` is load-bearing**, not incidental hardening: without it a container can re-address itself as a neighbour and spend that neighbour's credentials, so the whole model would be decorative. Set by `InstanceLifecycle.configureBranch` (a refused setting is retried without it and warned about, never fails the branch), re-armed on every stopped start by `InstanceLifecycle.prepareHostDevicesForStart` (so both `isx shell` and the TUI shell, and whatever merges them, must keep going through it -- `IpFilteringRearmTest`), which also restores it on instances the fallback below turned off. **Setting it succeeds even where it cannot be enforced** -- the failure appears only when the instance starts and Incus installs the per-NIC rules (`ebtables -t filter` under xtables, the nft equivalent otherwise), so a host without that kernel support would accept every branch and start none of them. The macOS appliance kernel needs `CONFIG_NF_TABLES_BRIDGE` for this (#905); its smoke test asserts it. `InstanceLifecycle.startInstance` is therefore the way isx starts an instance: it recognises that one failure, drops the setting, says plainly what is no longer enforced, and retries. Keep the match narrow -- it strips a security setting, so any other start failure must surface as itself.
- **Per-request credentials.** `RequestContext(domain, instanceName, creds, routing, usesDefaultCredentials)` replaces the bare `domain` parameter down `routeRequest -> handleApiRequest -> handleApiRequestWithBody -> sendApiRequest -> injectHeaders`. Routing is global (which domains are intercepted never varies by account); only the credential inside the entry does, so a pinned instance gets its own `ToolProxyRouting` built by the pure `buildRouting(list, warn)`. Everything derived from the config -- its serialized tree (the one every selection resolves against: serialize once per read, never per request), default credentials and routing, tool setups, the per-namespace indexes, and the `credentialsBySelection`/`mismatchesByInstance` caches (the first also caching a dangling pin's `UnknownAccountException`, #891) -- is one immutable `ConfigState`, built eagerly by `useConfig()` (the single path for the `MitmProxy(..., ConfigFingerprint.Loaded)` constructor and `reload()`) and **replaced whole on every reload**. A late request writes only into the old state's caches, so a rotated token is never put back. Never add a lazy read of config or tool setups: it escapes the fingerprint and can revert a reload (#837). The Vertex *token* cache stays global on purpose: `gcloud auth print-access-token` returns the host's gcloud user credential regardless of project, so only region/project come off the per-request creds. `authError` transitions are gated on `usesDefaultCredentials()` -- a pinned instance's broken token is reported to that instance, but must not set or clear the host's own auth status.
- **What a build derives from an account is stamped and reconciled.** `ToolSetup.bakedAccountIdentity()` returns Claude's `effectiveType()` (two accounts of one mode leave the image identical) and GitHub's account name plus `#` and a 12-hex SHA-256 fingerprint of its token and email (`user.name`/`user.email` come from whoever the token belongs to, so a token replaced in place with another user's is a change of identity too -- #281; a stamp without a fingerprint, from an older build, is re-derived once). Namespaces that bake nothing return `""` and are freely interchangeable. Stamped at build as `user.incus-spawn.account-identity.<ns>`. On a re-point, a tool that `canRebakeForAccount()` is asked to fix itself up -- `GhSetup.rebakeForAccount` clears the git identity and asks the API again, which resolves through the proxy and so answers for the new account by itself. `AccountSelection.staleIdentities` maps each stale namespace to the *account* to re-derive for, and `InstanceLifecycle.reconcileAccountIdentities` drives that, stamping back the tool's current identity, and is called from **all three** places a pin can change or take effect: `BranchCommand` after start, `AccountCommand`'s `set` when the instance is running, and `InstancePrep` on the next `isx shell`/`isx run`. All three are needed -- only the last catches an instance branched `--no-start`, and without the first two an instance used over `incus exec`, SSH or an IDE would keep committing as the template's account for as long as nobody happened to run `isx shell`. A tool that cannot (Claude: the mode is in `/etc/profile.d`, which a running agent has already read) has the swap refused by `AccountSelection.incompatibilityReason`. A child template's build re-derives an identity inherited from its parent that no longer matches (`BuildAccounts.settleIdentities`, from `BuildCommand`, *after* tool setup: a parent without gh still carries a GitHub stamp, and an identity written first would create the `.gitconfig` whose absence is how `GhSetup` knows to write its git defaults) -- the copy carries the parent's `.gitconfig`, which gh's setup would otherwise keep while the end-of-build stamp claimed the current identity. `GhSetup.rebakeForAccount` is a no-op where `gh` is not installed, since every build stamps every namespace. **Stamps come from the guest, not config.yaml:** `settleIdentities` asks each tool in `AccountSelection.rederivableNamespaces` (owning tool in the chain, can re-derive, known to `namespaceSetups`) `lacksBakedIdentity()` (one exec for gh), re-derives a missing identity an account can supply (`BuildAccounts.toRederive`; the stale test is `AccountSelection.needsRederive`, shared with the branch reconcile), and where none can, warns (`unbakedIdentityWarning`) and stamps `Metadata.ACCOUNT_IDENTITY_NONE` -- a token configured later is then an ordinary stale identity. A parent with an identity but no stamp keeps it. Never stamp the marker for a tool that cannot rebake: there a mismatched stamp refuses the account. Every build also stamps `Metadata.ACCOUNT_IDENTITY_VERIFIED`; an instance without it (template from an older isx) is `unverified` in `AccountSelection.identityReconcile`, checked in the guest once by `reconcileAccountIdentities` while an account is configured, repaired, and marked (and stamped with the account's identity when it has one, so a later change is still seen; any reconcile of an unmarked instance that did something marks it) -- once per instance, since the marker is written on the instance, never its template. The guest is asked *before* the wait for an address, which only re-deriving needs. An airgapped instance is never reconciled (`identityReconcile` returns nothing for it): it has no proxy to re-derive through and never gets an address, so the wait would cost every `isx shell` 30 s. A verified instance's reconcile is one read and no exec (`InstanceLifecycleRequestBudgetTest`); the plan is decided against the built-in tools that can re-derive (`AccountSelection.rederivableSetups`), and the tool definitions are read only when it finds something; `InstancePrep` and `BranchFlow` pass the read they already made (for `ensureReady`, and the pre-start prefetch), so on the shell and branch paths the reconcile costs no request. `ClaudeSetup`/`PiSetup` `envEntries(params, selection)` and `GhSetup.install(c, params, selection)` all take the **template's** account, not the global default.
- Three auth modes for Anthropic domains (priority: Vertex > OAuth > API key): OAuth mode strips `x-api-key` and injects `Authorization: Bearer <token>` for Claude Pro/Max users; Vertex mode does three-way routing -- passthrough for Vertex-formatted requests, standard-to-Vertex translation for `/v1/messages` (using `VERTEX_ALLOWED_FIELDS` body allowlist), and direct forwarding for non-messages endpoints; API key mode replaces `x-api-key` with the real key. Anthropic auth is declared via `ClaudeSetup.proxy()` with `type: anthropic` but remains hardcoded in `MitmProxy` (too complex for the generic tool proxy system); `buildRouting()` filters `type: anthropic` entries from domain maps
- GitHub, Bob, and Codex/OpenAI credential injection is handled via tool-contributed proxy entries (see Tool System), not hardcoded. `ToolProxyResolver.resolve(SpawnConfig)` resolves configuration from `value`/`config-path`, uses `${configKey}` template substitution in auth fields, and produces a per-domain `ResolvedToolProxy` list. `MitmProxy` stores these in `toolProxyByExactDomain` (exact matches) and `toolProxyWildcardSuffixes` (wildcard suffix matches); `findToolProxy()` does exact-then-wildcard lookup. `isInterceptedDomain()` is an instance method (not static) to include tool proxy domains alongside built-in ones. `ProxyCredentials` only has Anthropic-specific fields (`anthropicApiKey`, `oauthToken`, Vertex settings) -- `ghToken`/`bobApiKey`/`openaiApiKey` have been removed
- WebSocket passthrough: handles Upgrade requests by establishing an upstream WebSocket connection (with credential injection via both Anthropic auth and tool proxy lookup), then relaying frames bidirectionally with keepalive pings and close-code propagation. `routeWebSocket` completes the client's handshake (`completeHandshake`, the deprecated `ServerWebSocket.accept()` on purpose) before injecting anything or dialling, because the handler runs before Netty validates the handshake (#972); keep any new rejection (e.g. `reject(502)`) before it. Used by Codex CLI for `api.openai.com`
- Caches OCI blobs by SHA256, Maven/Gradle artifacts by repository path (confirmed with upstream per `ArtifactCacheTiers`, see below), and npm tarballs from `registry.npmjs.org` with ETag-based packument verification. npm's per-version shasum lookups go through `probeClient` (`fetchNpmVersion` → `fetchSmallBody`) like Maven/Gradle checksums; a `5xx` is asked once more (while over half the client's budget is left), since a failed lookup relays the tarball uncached and unresumable (#925). Never wait on the network inside an ordered `executeBlocking` (the default): every MITM connection shares one context and so one ordered queue, and a raw-socket lookup there ran every cold-install lookup one at a time (#960). The npm disk checks stay ordered on purpose, behind the packument's ETag write. All three commit through `Verification` (`fetchCacheAndServe`): nothing reaches the cache unverified. A cache download that stalls (`downloadIdleSeconds`, 20s, not counting our own backpressure) or breaks mid-body is resumed with `Range` + `If-Range` inside the same client response (`CachingDownload`, #925), since npm silently drops an optional dependency whose download breaks. The head wait and every resume fit into `clientSilenceBudgetSeconds` (110s since the client's request or last byte, threaded as `started` from `routeRequest`), below the MITM server's 120s idle timeout, which otherwise drops the client silently; the stall watchdog re-checks whenever a pause ends (`resumeWhenWritable`) so a late head cannot outsleep it. No validator (a strong ETag, or with no ETag a Last-Modified a second or more before `Date`), no resume, and then no stall cut either (`neverResumable`): only the client's budget ends it. A connect timeout cut short to fit the budget does not start the unreachable backoff (`requestWithAsyncDns`). Plain relays get the same budget with no resume (`RelayWatchdog` in `relayRequest`, #929): counted from the client's last byte, not while its body is still arriving, so uploads are not cut. `relayRequest` claims the request body on entry (`claimBody`) and `sendWithBody` composes on that `Future<Buffer>`; never read `clientReq.body()` after an async step, since Vert.x drops a body nobody is reading and the relay hangs (#1164). So a request with a body is relayed from `routeRequest` before anything waits: to a caching domain (`cacheHandler`, the one list of them) it never reaches the cache handlers, which wait. The relay's budget runs from the moment that body has all arrived, connect included. Don't lower the upstream client's read-idle timeout instead: slow uploads get no bytes back
- **Maven/Gradle cache integrity** (#555, DESIGN.md "Maven/Gradle cache integrity"): serve a cached artifact only when a direct fetch would have returned the same bytes at its last confirmation with upstream, and that confirmation is recent enough. **`ArtifactCacheTiers`** (`artifact-cache:` `fresh`, default 2h; `max-stale`, default 7d) decides from the stored checksum's mtime, which `VerifiedArtifactStore` sets on commit and renews (best-effort) only on a match from an answer that could have evicted (`mayEvict`): fresh is served with no request, stale is served and confirmed in the background (single-flight, at most 16 in flight, the rest queued; a change evicts for the next request, an inconclusive answer expires the confirmation), older is **confirmed before serving**. `Revalidation.mayWithdraw` domains (Plugin Portal) never get the tiers. `artifact-cache:` stays a raw value in `SpawnConfig`: a typed binding would let a mistyped section fail the whole config.yaml. Hits are counted in `ArtifactCacheStats` and logged as one summary at most every 5 s, only after activity; don't add a per-hit log line back. Older is confirmed as `Revalidation` says per domain: `HEAD_CHECKSUM` (Central: a `HEAD`'s `X-Checksum-SHA1`, falling back to `.sha1`) or `SIDECAR` (portal, Gradle distributions). A domain without an entry is never cached. A miss is only the GET, committed if it matches the same response's `X-Checksum-SHA1` or the sidecar fetched afterwards; no usable checksum means served but not cached. Past the tiers, only an unreachable upstream (`SidecarAnswer.unreachable()`: connect failure or 5xx; 30s per-domain backoff) serves unconfirmed. `X-Checksum-SHA1` is what makes Maven skip its `.sha1` request: for a copy served on a trusted confirmation (`serveTrusted`) it is the stored checksum, and sidecar requests get the stored copy too, or Maven would pay the round trip the tiers save. For any other copy it must be upstream's **current** value, never synthesized from the store, which would turn the client's check against upstream into a check against our own cache. `Revalidation` is also the caching allowlist, and its javadoc states why a domain must be vetted even though hits are confirmed: offline serves are unconfirmed, and serves within the tiers not confirmed now (so they rely on the repository not changing or withdrawing releases), the confirmation must be sound for that repository (`SIDECAR` only where artifact and sidecar are published together and never replaced), and the cache is shared across instances without per-client authorization (public repositories only). Keep those reasons, not "immutability", in comments. `probeClient` (h2) needs its connection-level `readIdleTimeout` below `probeOptions()`' request timeout: it fires only while an exchange waits, and is the only thing that evicts a silently dead h2 connection (a request timeout resets just its stream). Keep `setHttp2MaxPoolSize` above 1, or bursts to HTTP/1.1-only or unreachable hosts serialize. `~/.m2` imports copy/reflink, never hardlink. Commit/reconcile/evict go through `VerifiedArtifactStore`'s striped lock; don't touch the cache files around it
- **Proxy lifecycle locking**: `ProxyService` guards mutating operations (`restart`, `stop`, `install`, `uninstall`, `startService`, `reinstallIfChanged`, `upgradeIfNeeded`) with a `HostLock` (`proxy.lock` in `configDir()`). Public methods acquire the lock then delegate to private `*Locked()` variants, because `HostLock` is not reentrant. When adding new operations that modify proxy service state, follow the same pattern.
- **The service execs `isx-proxy`, never `isx proxy start`**: the CLI dropped Vert.x when the proxy became its own module, so it cannot serve the proxy in-process. `install()` resolves `resolveProxyBinaryPath()` first and refuses to write the unit/plist without one (`printMissingProxyBinary()` names the JBang aliases, since JBang installs each separately -- issue #701). A unit exec'ing `isx proxy start` restarts itself forever: the command sees the service installed and unhealthy and restarts the unit it is running under, with `reset-failed` clearing systemd's rate limiter each pass. Units already on disk are covered three ways: `ProxyStartCommand` resolves the proxy binary *before* any service management and exits `EXIT_CONFIG` when it is missing (restarting cannot fix an absent binary); `ProxyService.isSupervisedInvocation()` matches systemd's `INVOCATION_ID` against the proxy unit's own invocation (Linux) or this process's own pid against what `launchctl print` reports for the job (macOS, #977 -- restarting the job from inside it can end this very process via `bootout` before it reloads) so a legacy unit/plist's `isx proxy start` launches the proxy instead of restarting itself; and on macOS, where launchd has no `RestartPreventExitStatus` (a `KeepAlive` job exiting 78 is simply restarted) and `RunAtLoad` would revive a booted-out job at the next login, `haltUnusableMacOsService()` boots the job out **and** deletes the plist, declining whenever the proxy still answers on 127.0.0.1. `upgradeIfNeeded()`/`reinstallIfChanged()` call it before `needsMacOsPlistUpdate()`, which cannot describe a plist whose binary is gone. `startScriptIsStale()` compares the exec line, which no legacy `isx proxy start` script can match, so upgrades rewrite them. The supervised branch never calls `restartLocked()` (it runs in the foreground instead), so it never rewrites its own stale plist that way either; `ProxyService.migrateMacOsPlistIfSupervised()` rewrites it directly, under the proxy lock, with no bootout or bootstrap, so the next login execs `isx-proxy`. `install()` and `isx proxy install` (before its running-service path) refuse with "run `isx init` first" until `Environment.hasBeenInitialized()` (`ProxyService.initComplete()`, #968): the proxy exits `EXIT_CONFIG` before init, so a service installed or restarted then could only report "not responding". So does every restart and start (#1048): `restartLocked()` (under the lock, after `restartIfUnhealthy`'s health recheck), `startService()`, and `reinstallIfChanged()`/`upgradeIfNeeded()` before they rewrite the service files (after the macOS halt). After an `INIT_VERSION` bump the proxy still running is a working one; refusing keeps it. Paths the TUI reaches pass a sink (`initComplete(log)`). `isx init`'s firewall step defers its restart when the marker is stale; `completeWithProxyService` restarts a running service it found with a stale marker once the marker is written (read from the marker, so an aborted run's restart is not lost). The TUI names `isx init` on its status line when the auto-restart was refused. `ProxyService.replaceCommandRunner` swaps `runQuiet` for a recorder so `ProxyServiceInitGateTest` fails, rather than restarts a real service, if a guard regresses.
- **launchd: `bootout` is asynchronous, so restarts use `kickstart -k`** (`LaunchdJob`, #916). `launchctl bootout` returns as soon as the job was told to go; a process that ignores SIGTERM (a hung proxy) is killed only about 5 s later, and until then a `bootstrap` fails with `5: Input/output error` while `launchctl print` still finds the job. The old `bootout` + `bootstrap` restart therefore reported success and left nothing loaded. `LaunchdJob.restart` restarts a loaded job in place (`kickstart -k`, no unload, nothing to race); only a changed plist is reloaded, and then it waits (`UNLOAD_POLLS`, 10 s) until `print` stops finding the job before `bootstrap` + `kickstart`. `restart`'s `kickstart -k` refuses with exit 37 for a job that is already being unloaded (after `isx proxy stop` on a hung proxy); that one waits for it to be gone and loads it afresh, same as a changed plist. `start` never reaches `kickstart` at all -- it is only `load` (`bootstrap` + `kickstart`), reached when `startService()` finds nothing loaded. Any other `kickstart` failure leaves the job loaded. Success is `launchctl` returning 0 **and** the job still `state = running` under the same pid half a second later (launchd shows a proxy that is about to exit as running), never "`print` succeeded" -- `isActive()` still means only "loaded". Both `start` and `restart` return a `LaunchdJob.Outcome` (`RUNNING`/`STILL_UNLOADING`/`FAILED`/`EXITED`), not a bare boolean: `isActive()` alone cannot tell a job still being unloaded apart from one that loaded fine and is merely unhealthy, and `installMacOs` needs that distinction to report the right cause. `FAILED` is `launchctl` refusing; `EXITED` is a job that was loaded and started but did not stay up, which launchd retries after `ThrottleInterval`. Only `RUNNING` is `up()`, but `startService()` answers with `launched()` (`RUNNING` or `EXITED`), so `isx proxy start` waits for launchd's retry through `awaitStarted` instead of printing "failed to start" about a proxy that comes up ten seconds later (#1098); `restart`'s callers keep `up()`. `restartLocked`'s `forceReload` parameter, not a plist comparison inside it, decides whether to reload: `reinstallIfChanged` and `upgradeIfNeeded` pass it whenever *they* already know a reload is needed -- including health-assessed drift `needsMacOsPlistUpdate()` itself cannot see -- so callers must not separately rewrite the plist and expect `restartLocked` to notice on its own. `bootstrap` also answers 5 for a job that is already loaded, so never bootstrap without checking `isLoaded()`. `kickstart -k` honours `ThrottleInterval`: on a job started under 10 s ago it blocks for the remainder. The same interval bounds every wait for health after the job is started: on macOS `ProxyService.awaitStarted` stretches them past `LAUNCHD_THROTTLE_SECONDS` (which the plist is generated from), so a failed first start is not reported before launchd's retry, and a wait that still times out prints `LaunchdJob.lastRun()` (`state`, `runs`, and `last exit code` or, for a run a signal ended, `last terminating signal`, #969). The price is that a proxy which never comes up is reported after 15 s on macOS, not 5 to 10. `tryAutoRestart` (`ProxyHealthCheck`) re-checks `/health` under `proxy.lock` before restarting (`restartIfUnhealthy`), so a second `isx` command arriving while the first is still restarting a proxy that is now healthy does not `kickstart` it again and cut every connection. Tests replace `LaunchdJob.Launchctl` with a fake launchd (`LaunchdJobTest`); `restartIfUnhealthy`'s restart action is itself replaceable so a test proving the health recheck skips a restart never touches a real service (`ProxyServiceTest`). `installMacOs` reloads the proxy job through it too, and writes the plist only right before that, because `restartLocked` takes a plist that is current on disk for the one the job runs. Still calling `launchctl` directly: `stopLocked`, `uninstallMacOs` and `haltUnusableMacOsService`, which only unload, and the VM agent in `installMacOs`: a one-shot `RunAtLoad` job that is never kickstarted or expected to stay running, so it does `bootout`, waits until `print` stops finding the job (`waitForJobUnloaded`, up to 20 s), then `bootstrap`, and warns when that `bootstrap` fails (#977: a reinstall while `isx vm start` was still running under the old job otherwise left no VM agent loaded).
- **The foreground `isx proxy start` stops its child on shutdown**: `ProxyStartCommand.ForegroundProxy` registers a hook, before it starts the child, that sends the `isx-proxy` child SIGTERM and SIGKILLs it after 15 s (and skips the abnormal-exit diagnosis, since that stop was asked for), so killing the CLI alone does not orphan a proxy that keeps the ports (#882). `ProxyStartForegroundTest` drives it in a separate JVM. For a CLI that runs no hook (SIGKILL, OOM), `foregroundCommand()` passes `--exit-with-pid <cli pid>`, an internal argument (not in `--help`), and the proxy exits once that pid is no longer among its ancestors (`ExitWith`, #923). Ancestry, never liveness: `onExit()` counts an unreaped zombie CLI as alive. The service units must never pass it.
- **Bridge DNS is `address=/<d>/<gateway>` + `local=/<d>/`** per intercepted domain, inside a `# BEGIN`/`# END incus-spawn intercepted domains` block in `raw.dnsmasq` (`BridgeDns`; `ProxyConfig.writeBridgeDns()`/`clearBridgeDns()` replace or remove only that block). The `local=` line makes AAAA/HTTPS answer NODATA instead of being forwarded upstream, where real IPv6 addresses would bypass the proxy. Never go back to `address=/<d>/::`: `::` reads as loopback, so a nested isx's `DownloadCache` refused every intercepted domain (#814). Never infer ownership from line shapes: an orphaned `local=/<d>/` answers NXDOMAIN for the whole domain. The pre-block layout is detected by its `::` lines and migrated. Anything that rewrites the block takes its domains from `ToolProxyResolver.resolvedDomains()` (all accounts, as the proxy does), never the default account alone. On Linux the proxy points the block at the gateway it already resolved and listens on (`ProxyMain.Addresses`, whose writers startup uses and `MitmProxy` is handed for reloads; `--gateway-ip` sets it, and must be a unicast IPv4 address in canonical form or the proxy exits `EXIT_CONFIG`; DESIGN.md says why), never a second bridge lookup, which ignored the override and failed on a bridge with no address (#892). As the credential listener's bind address, a Linux `--gateway-ip` must also be private (RFC 1918), loopback, or the bridge's current gateway (`BridgeAddress.read()`, never the cached one), else `EXIT_CONFIG`, or exit 1 when that comparison needs a bridge read that fails; a private override is accepted without reading the bridge, so it still works around #892 (#1022). On macOS it looks up the VM's own bridge, and `--gateway-ip`, the credential listener's bind address there, must equal the host's VM-bridge address (`VmNetwork.discoverHostBridgeIp()`) or the proxy exits `EXIT_CONFIG`: a wildcard or LAN address would serve the default accounts to other hosts (#937). CLI writers still use the detected gateway (#933). A failed health probe with the block pointing at another address that the host no longer has but that still has a listener on the health port (`/proc/net/tcp{,6}`, since that address no longer answers) is `STALE_GATEWAY`, not `STALE_DNS`: the proxy is up and needs a restart (#919). The auto-restart (`requireProxy`, `checkOrWarn`, the TUI) restarts the service for it only when the service is active (`serviceRestartCanHelp`): with a foreground proxy it would start a second one beside it. A proxy whose gateway came from the bridge (no `--gateway-ip`, Linux) also notices by itself (#966): `Addresses.movedTo()` re-reads the bridge every `GATEWAY_CHECK_MILLIS` (60 s) and before a reload rewrites the block, and on a different address it skips the write (`GatewayMoved`), stops, and exits 1 so `Restart=on-failure` starts it on the new address. An unreadable bridge or one with no address is not a move, and an explicit `--gateway-ip` is never compared (#933). Exit-and-restart, not rebinding in place: the startup path already moves the listener, health endpoint and block together.
- **Redirect rule cleanup**: `ProxyService.uninstall(IncusClient)` removes the service **and** unconditionally cleans up PREROUTING redirect rules (`ProxyConfig.clearRedirectRules()`) and bridge DNS overrides (`ProxyConfig.clearBridgeDns()`). `clearRedirectRules()` attempts both firewalld and UFW independently (not else-if) so a system with firewalld installed but inactive still reaches UFW cleanup. Firewalld cleanup falls back to editing the persistent `/etc/firewalld/direct.xml` when the daemon is not running. `runQuiet()` returns `boolean` success; cleanup callers check and warn on failure. `clearRedirectRules()` returns `boolean` so callers like `ResetCommand` can propagate cleanup failures. The no-arg `uninstall()` is private — callers must pass an `IncusClient` so DNS cleanup can reach the bridge.
- **`/activity` (#898)** serves `ApiActivity`: per instance, Messages API creates only (`ApiActivity.isModelCall`), counted in `handleApiRequestWithBody` (`beginModelCall`) and ended once on the client response's end or close, with tokens read from 2xx responses' `usage` by `UsageTap` as `pipeResponse` relays them (cumulative stream counts: keep the max per field). Counted calls go upstream with `Accept-Encoding: identity`; nothing else's headers change. Each instance's counters carry their own creation time (`counting_since`), never the proxy's start, and a read creates them for every instance the registry knows, so a known instance always has one: a read drops those of instances the registry no longer lists, but only idle ones and through `computeIfPresent` against `begin`'s `compute`, and counters made again must show a new stamp or a client's before/after subtraction goes wrong. Counters belong to one incarnation of a name (`InstanceRegistry.incarnations()`, the listing's `created_at`): a call or read naming another starts them afresh, so a hand-named instance branched again never inherits the old one's counts (#1063). A call's incarnation comes from the lookup that named it (`InstanceRegistry.resolve`, in `RequestContext`), never from a second snapshot read; counters never go back to an earlier registry view (`InstanceRegistry.Incarnations.view`; a late call of the destroyed instance is counted nowhere), or a call and a read from different snapshots would reset each other. Order by view, never by `created_at`: a rename hands a name an older one. The prune obeys views too: a read never drops counters a later listing made. Host callers only; a container gets a 404. `ProxyActivity` (`common`) is the CLI's reader of the same JSON -- `ApiActivityTest` pins the round trip.
- `/health` includes the proxy's `pid` only for host callers (`MitmProxy.isHostCaller`); keep any other host-only detail behind the same check, since containers reach this endpoint. `ProxyService.signalAccountRefresh()` reads it at signalling time and falls back to `fuser` for older proxies, as `isx proxy stop` does for a proxy started by hand (`stopManualProxy`, #155: `fuser` finds nothing on macOS or without psmisc). Tests must never send it: `TempHome` (common, `lifecycle`) and `IsolatedHome` (cli, `command`) swap the signaller for a counter (`ProxyService.replaceAccountRefreshSignal`, `proxySignals()`) for the test classes that `@ExtendWith` them. Protection is opt-in, so a test reaching any caller -- branch, destroy, clean, an account change -- must run under one of them, never add a seam of its own (#871).
