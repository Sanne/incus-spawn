# Incus Interaction

`IncusClient` communicates with the Incus daemon via its REST API. On Linux, requests go over a Unix domain socket (`UnixSocketTransport`); on macOS, over a vsock tunnel exposed as a Unix socket (same `UnixSocketTransport`). `IncusApi.tryConnect()` selects Linux Unix sockets -> vsock Unix socket; there is no HTTPS fallback (the old HTTPS-over-TCP path was removed -- it hit macOS Local Network prompts and VPN socket filters, and two transports made field issues undiagnosable; `HttpsTransport` remains in the tree but is unwired). `IncusApi` handles request serialization, async operation waiting, and WebSocket-based exec (capture, stream, PTY). `Container` is a helper for running commands inside a specific container (`exec`, `runAsUser`, `runInteractive`). The `incus` CLI binary is not required at runtime.

**macOS vsock robustness**: the vfkit vsock tunnel does not reliably propagate connection close/EOF, which drives several design choices (see DESIGN.md "Transport" and appliance/DESIGN.md):
- **Exec completion via `/wait`, not close frames.** `IncusApi.execWebSocket` unifies capture/stream/bidirectional exec and takes the operation `/wait` endpoint (daemon operation state over HTTP) as the authoritative completion + exit-code signal, then drains and force-closes the data sockets -- so a lost close frame can't hang exec. Every exec fd is keepalive-pinged; the drain is adaptive.
- **Long-lived event subscription.** `IncusApi.openEvents(types)` (public via `IncusClient.openLifecycleEvents()`, returning `IncusEventStream`) is the one WebSocket meant to stay open indefinitely (the TUI's `InstanceEventWatcher`). Incus pings its event listeners about every 10s and drops those that never answer, so `readMessage()` answers PINGs with PONGs (`ControlFrames`) and reassembles fragmented frames (one JSON document per message). **`readPayload()` -- the exec/shell path -- deliberately never writes**: it skips PINGs exactly as before event subscriptions existed, because a PONG sent from the reader thread would queue behind a stdin write holding `writeLock`, and Incus doesn't ping exec sockets anyway. Keep the two paths separate. The event stream also pings every 15s (keeps `socat -T` from reaping it) and its keepalive closes the stream after 50s with nothing received (`millisSinceLastReceived()`, fed only by `readMessage()`) -- in a `finally`, so the stream ends whenever the keepalive does -- so a half-open vsock stream reads as end-of-stream instead of blocking forever. Reconnect policy (bounded; gives up for the session) lives in the TUI's `InstanceEventWatcher`.
- **Keep-alive connection cache.** Short request-path calls (`get`/`post`/`/wait`) reuse a warm connection via `requestPooled` -> `ConnectionPool`/`KeepAliveConnection` instead of reconnecting per call; the exec WebSocket fds are per-operation and not pooled.
- **One strict HTTP parser.** `HttpResponseReader` parses every response on the Unix-socket paths (one-shot, `KeepAliveConnection`, WebSocket handshake). EOF anywhere before the response is complete is an `EOFException`, never a shorter success (`NoResponseException` = nothing received, the keep-alive path's retry-safe case); only close-framed bodies may end at EOF. `wsReadFrame` applies the same rule inside a frame. `openWebSocket` bounds connect + handshake with the transport timeout via `Watchdog`, whose `cancel()` returning false means the deadline won and the channel must not be handed on. Do not add a second parser, or read EOF as a blank line -- that is how a dropped upgrade became an exec with silently empty output.
- **Tested without a Mac.** `LossyIncusServer` (test scope) is a fake Incus on a real Unix socket that misbehaves like the vfkit tunnel (no close frames/EOF, output after exit, accept-then-silent, stalls, dropped idle connections, truncated bodies). `IncusApiLossyTunnelTest`, `UnixSocketTransportTest`, `ConnectionPoolTest` and `KeepAliveConnectionTest` run against it in `unit-tests`. A change to any compensation above needs a test there; tests that shorten production intervals use the package-private seams (`IncusApi(transport, pingIntervalMs)`, `ConnectionPool(idleTtlNanos)`, `IncusApi.tryConnect(List)`) rather than sleeping. Every test asserts `UnixSocketTransport.openConnectionCount()` returns to its baseline, so a leaked permit on a failure path fails the build. The guest half (the in-VM forwarder, `isx-agent`, the `-T` backstop, recovery) runs in `integration-tests` against the real appliance over a vsock-bridged QEMU boot (`appliance/test-tunnel.sh`, see `ci.md`). Only vfkit itself is untested, and cannot be on hosted runners (#774).
- **Never open a tunnel connection without sending a request.** incusd's local listener (`StarttlsListener`) peeks 8 bytes inside `Accept()` with no deadline, so one connection that has sent nothing stalls *every new* API connection until it speaks or closes. On Linux the close arrives at once; through vfkit it may not, and then the forwarder holds that silent connection until `socat -T` reaps it -- the whole API wedged for up to 180s, cleared early only by `forwarder-restart`. So no bare connect-and-close probes: `IncusApi.diagnoseVsock` sends a real `GET /1.0` (`IncusApiLossyTunnelTest` asserts the request arrives). Upstream: LXD fixed the same code (canonical/lxd#18705); incus had not as of 7.5.1. incusd also closes idle keep-alive connections after 30s (`IdleTimeout`), which is why `ConnectionPool`'s 5s TTL must stay well under it.
- **Forwarder leak + recovery.** The same close-propagation gap makes the in-VM `socat` forwarder leak connections. A `socat -T` inactivity backstop reaps them (the forwarder and agent listeners also set `backlog=128`: socat's default of 5 refused concurrent connects, and one exec opens about five); `isx doctor` diagnoses it (host-side connection gauge in `UnixSocketTransport` / `vm status` vs the in-VM `isx-agent`'s socat count, localizing vfkit vs forwarder) and can restart the forwarder via the agent **without rebooting the VM**. `ClientLog` is a file-only (TUI-safe) diagnostic log for expected-but-noisy events like stale-connection recycling. The agent (`appliance/root/usr/local/sbin/isx-agent`, host side `VmAgentClient`) is an allowlisted one-verb-per-connection dispatcher -- `ping`, `version` (returns the appliance version from `/etc/isx-version`, cached by `VmAgentClient.applianceVersion()`; used to detect CLI↔appliance version skew in `ensureRunning`, `isx doctor`, `isx vm status`, and the TUI), `socat-count`, `sshd-status`, `forwarder-restart`, `btrfs-usage <pool> [sync]` (returns the pool's `btrfs qgroup show`/`subvolume list` output for disk accounting, since only the in-VM root agent can read the pool; the allowlisted `sync` second token forces a commit first), `btrfs-status <pool>` (the kernel's qgroup accounting flags from sysfs as `key=value` lines -- `enabled`, `inconsistent`, `mode`, `drop_subtree_threshold` -- resolved via the same mountinfo-source-device lookup as `BtrfsSysfs.java`; keep the two in step) and `btrfs-rescan <pool>` (starts a background `btrfs quota rescan`, replying `started`/`running`/`error: ...`) -- intentionally NOT a general guest-exec channel. Pool-name validation is shared by the three `btrfs-*` verbs (`valid_pool`).

**VM lifecycle locking**: `VmManager` guards mutating operations (`start`, `stop`, `restart`, `ensureRunning`) with a `HostLock` (`vm.lock` in `vmStateDir()`). Public methods acquire the lock then delegate to private `*Locked()` variants, because `HostLock` is not reentrant: re-acquiring on the same thread throws. When adding new operations that modify VM state, follow the same pattern: public wrapper with `acquireVmLock()` in try-with-resources, private `*Locked()` implementation. If an operation calls another mutating method (e.g. `restart` calls `stopLocked` + `startLocked`), use the locked variant directly. `resetDataDisk` (`isx vm reset`) follows the same shape: stop, wait for the hypervisor to exit, replace the data disk with a blank one of the same size, start, all under one lock.

**Host locks**: every cross-process mutex goes through `HostLock.acquire(file, activity, log)` (`common/.../util/`): an `fcntl` file lock behind a per-path in-process `ReentrantLock` (a second `tryLock` from one JVM throws rather than waits, and closing any channel on the file drops the process's lock), keyed by the file's real path, polling with backoff from 10 ms capped at 50 ms (`fcntl` has no queue: a waiter backed off further keeps losing to newcomers), 30 s timeout. The lock is per user (under `$HOME`). Do not open-code another `FileChannel.tryLock` loop. `FlockInstanceLockManager` (cli, per-instance TUI locks) is a different shape and stays separate.

**Static IP claims are locked**: the proxy identifies an instance by its source address, so no two NICs may share an `ipv4.address`. Addresses come only from `StaticIpAllocator.claim(incus, bridge, ip -> write)`, which holds a `HostLock` (`.static-ip.lock` in `Environment.lockDir()`: dot-prefixed so no instance's TUI lock, `<instance>.lock` in the same directory, can be the same file) from the listing until the callback's NIC write returns (#815). A nested claim throws: the outer address is not written yet, so the inner one would get the same. `IncusClient.copy()` is the other half: the copy request drops `ipv4.address` from the source's own NICs and unsets `static-ip`/`static-gateway` (`CopyPlan.addressedNics`, from the source read `planCopy` already makes), since Incus accepts a copy whose NIC conflicts with another -- it only logs it -- and a branch of a branch would otherwise hold its source's address until `configureBranch`, or for good if that never runs. **Read the bridge once**: `BridgeAddress.read/require` gives gateway, subnet and prefix length from one request; a flow needing more than one of them passes the record along rather than calling `ProxyConfig.resolveGatewayIp` and `bridgePrefixLen` separately. Every isx of this user queues on this lock, so read everything that does not depend on the address before the claim. The listing fails closed; an unusable lock file does not: `HostLock.acquireOrDegrade` warns once and keeps only the in-process lock, since Incus's 409 still refuses the collision. Anything the claim or the stale-subnet repair reports goes through a `StaticIpAllocator.Output` (step, warn), never straight to stdout/stderr: the TUI runs that repair on its own screen. The static `.network` is pushed root `0644` explicitly (`systemd-networkd` cannot read `0600`). Incus's own 409 on a duplicate address covers writers outside the lock. Tests that reach `claim()` through `configureBranch` run under `@ExtendWith(TempHome.class)` so they never take the developer's real lock. See DESIGN.md "Static IP assignment".

**Post-launch readiness**: every code path that freshly launches the VM must verify it actually booted — `startLocked()` only spawns the hypervisor process and cannot detect an immediate crash or a guest that fails to reach Incus. Callers use the `StartResult` enum to distinguish `LAUNCHED` (needs readiness wait) from `ALREADY_RUNNING` (VM process exists, no launch happened). Call `awaitReady()` (or the equivalent `waitUntilReady()` loop) for `LAUNCHED` within the lock scope so a concurrent `restart()` cannot kill the VM mid-boot. The `ALREADY_RUNNING` path does not probe Incus — that is `ensureRunning()`'s job, with its own recovery logic.

**Instance readiness**: `IncusClient.waitForReady` is the only "wait until it answers exec" -- do not reintroduce a private copy (BuildCommand had one). Containers get 30s, VMs 120s; the type comes from the status GET after a failed probe, so the happy path costs no extra request, and a VM is then probed every 250ms rather than 50ms. For a VM it polls the console log for `VmAgentFailure` signatures and fails fast (after a 20s restart grace) with the matched lines (`VmAgentFailure`, reusable by a future `isx doctor` check); every VM failure names the agent and `incus console <n> --show-log` (#844). Timings are a `ReadyTimeouts` record that `WaitForReadyTest` shortens through the package-private setter. A running VM whose agent does not answer on `isx shell`/`isx run`/the TUI goes through `InstanceLifecycle.ensureReady` -> `lifecycle/VmAgentRecovery.restartForAgent` -- never a bare `forceStop` + start: it refuses when the console log shows a `VmAgentFailure` the agent has not since recovered from (`unrecoveredLines`, after `waitForReady`'s grace), restarts at most once per boot (the restarted boot's `IncusClient.pid` is stamped as `Metadata.AGENT_RESTART_BOOT`), and stops gracefully before forcing (#843).

**Storage pool awareness**: On a CoW-capable pool (btrfs/zfs/lvm), Incus implements a same-pool `type: copy` as a native snapshot (e.g. `btrfs subvolume snapshot`) -- no explicit snapshot API call is needed. Full copies only happen when (1) there is no CoW pool (the `dir` driver rsyncs), or (2) the source's root disk is on a different pool than the copy target (cross-pool migration). A CoW pool is **required** for instance creation and copying -- `requireCowPool()` throws with a specific diagnostic (pool listing failed vs. no CoW pool found) instead of silently falling back to the profile default. `findCowPool()` (nullable) remains for callers that handle absence gracefully (cleanup, diagnostics, TUI display, image import). `IncusClient.copy()` follows the source's pool via `planCopy()`: if the source's root disk is on a CoW pool, the copy targets the same pool; otherwise it targets the first CoW pool (cross-pool full copy). `planCopy()` also throws if no CoW pool exists. `importImage()` sends `X-Incus-Pool` targeting the CoW pool so base images don't pile up on a non-CoW default. `isx branch` and `BuildCommand.buildFromParent()` warn when a copy will be full (non-CoW), and `isx doctor` surfaces three cases -- no CoW pool (FAIL with Linux remediation), default profile root disk on a non-CoW pool (WARN with auto-fix remediation), and instances on non-CoW pools (WARN with rebuild/move guidance). `isCowDriver()` and `rootDiskPoolFromDevices()` are the unit-testable helpers.

**Default profile pool upgrade**: When Incus is set up before `isx init` (common on Ubuntu, where `incus admin init --minimal` creates a `default` dir pool), the default profile's root disk may point to the `dir` pool even after init creates a `cow` btrfs pool. `ensureDefaultProfile()` now detects this: after ensuring the profile has a root disk and NIC, `upgradeProfilePoolIfNeeded()` checks whether the existing root disk is on a non-CoW pool while a CoW pool is available, and updates it. This only upgrades (non-CoW -> CoW), never downgrades. `IncusClient.updateProfileRootDiskPool()` handles the PATCH, finding the root disk device by type rather than assuming a conventional name.

**Orphaned subvolumes and dangling records** (#717): `InstanceSubvolumes` compares a btrfs pool's top-level instance subvolumes (names-only parse of `btrfs subvolume list` via `BtrfsUsage.subvolumeList`, anchored at the pool so a guest's nested Incus pool is ignored) with Incus's volumes (all projects, `<project>_<name>` on disk) and instances. `IncusClient.scanSubvolumes()` returns the comparison for the CoW pool; `IncusClient.delete` refuses a record whose subvolume is missing (`DanglingRecordException`, before any DELETE), `IncusClient.rename` fails when the record moved but the subvolume did not, and `storageOnDisk(name)` answers the same question for one instance. `BtrfsUsage.parse` places subvolumes with the same anchored parser, so rfer sizes and the orphan scan agree on names. All of it **fails open** when the pool cannot be listed. Do not reuse `BtrfsUsage.parse` for this: it drops subvolumes without a qgroup row. See DESIGN.md "Orphaned subvolumes and dangling records".

**Request budgets**: each Incus round trip on the start/shell/branch path adds latency the user waits through. `InstanceLifecycleRequestBudgetTest` pins exact request counts using `FakeIncusDaemon` (test scope, an in-memory `IncusTransport`); a change that adds requests to a covered flow fails it, and one that removes requests must lower the budget. Give a new user-facing flow in `common` a budget, and prefer one `instanceMetadata`/`configByPrefix` read over several `configGet` calls. See DESIGN.md "Request budgets".

**Batch instance writes**: every instance PATCH/PUT costs Incus a backup-file rewrite (~11-13 ms on btrfs), so a flow making several changes collects them in an `InstanceUpdate` and sends one `IncusClient.update()` against a single `instanceMetadata` read -- a PATCH, or one PUT only when a device the instance declares must be removed. `InstanceLifecycle.configureBranch` configures every new branch (CLI and TUI) this way in one write; add new pre-start branch settings there rather than as another write. See DESIGN.md "Why a branch is configured in one write". Every branch, from `isx branch` or the TUI, goes through `lifecycle/BranchFlow` (`preflight()` refuses before anything exists, `create()` copies, configures and starts); a front end supplies only its inputs and what follows (the shell), never its own copy of the steps -- the TUI's used to be one, and skipped the account selection and proxy refresh (#800). The credential check runs on the selection the branch will be stamped with (template, source pins, `--account`) against the source's leaf template; the TUI's branch dialog asks the same question through `BranchFlow.credentialProblem()` before releasing the terminal (#793, `config/CredentialCheck`). Metadata a caller must stamp on its branch goes in `BranchFlow.Request.extraConfig`, which rides both the copy request (`IncusClient.copy(..., configOverrides)`: Incus lays the request's `config` over the source's, so the instance never exists unstamped) and `BranchSettings.extraConfig` in the one write. Deletion goes through `lifecycle/InstanceDestroyer.deleteHeld()` with the caller holding the instance lock, then one `refreshProxy()` per batch (the TUI, which refreshes its view mid-delete, does the steps itself and calls `refreshProxy()` after).

**No file push right before a start**: Incus's forkfile (which serves file pushes to a stopped container) must exit before the instance starts, and re-checks only once a second while a push is still flushing -- so a push immediately before `start` costs a full second. Put anything the instance needs after start into `buildSetupScript` (one exec, heredocs via `Container.heredoc`), and keep `InstanceLifecycle.prefetchAndStart()` push-free. A file that must exist at boot (the static `.network`, GUI passthrough files) is pushed early in the branch flow, never as its last pre-start step. See DESIGN.md "Why nothing is pushed into an instance just before it starts".
